# TrillionAI revenue operator

A persistent Node/TypeScript and PostgreSQL operator with a Flutter owner client. Its mission is continuous legitimate revenue, verified customer delivery and retention. Starts paused; no customers, sales or readiness evidence are seeded.

This service was developed while a separate implementation was pushed to repository main. It is isolated in `services/revenue-operator`, with the private `manager_operator` database schema. Existing root/backend and root/frontend code is preserved. **Run only one chosen operator against real services.** This is a reviewable normalized implementation, not an automatic migration of the root runtime's aggregate state. Data migration, endpoint convergence and ecosystem adapters remain release blockers.

## Run

Requires Node 22+, PostgreSQL 17 and a continuously running host. From this directory:

```sh
npm ci
npm run build
npm test
```

Using a migration administrator connection through the secret store, run `npm run migrate`. Apply `backend/sql/runtime-role.sql` once, attach the dedicated runtime LOGIN user to `manager_operator_runtime`, and replace `DATABASE_URL` with that user's TLS connection. The backend never runs migrations automatically. Provide the variables in `.env.example` through the host secret store, then `npm start`. Environment files are not loaded implicitly. Docker supports restart policies supplied by the host. `/health` is process liveness; `/ready` tests database access. `/v1/state` includes worker/planner heartbeats; alert on worker age over 120 seconds.

A ChatGPT session does not host the 24/7 runtime. No paid infrastructure is provisioned by this change. Backups, TLS, rate limiting, secret rotation, alert routing and restore qualification must be configured before production.

## Owner client

The Flutter client supports sign-in, Run/Pause, currency-separated revenue, approvals, offers, and failed task retries. Owner IDs are enforced by the backend using Supabase Auth `/user`, not client-provided metadata. Access/refresh tokens stay in process memory and are cleared on logout. Configure an owner account and authentication recovery before deployment. MFA enforcement is not implemented here.

```sh
cd frontend
flutter create --platforms=web,android,ios --project-name trillionai_manager .
flutter pub get
flutter analyze
flutter test
flutter build web --dart-define=MANAGER_URL=https://YOUR_API --dart-define=SUPABASE_URL=https://YOUR_PROJECT.supabase.co --dart-define=SUPABASE_PUBLISHABLE_KEY=YOUR_PUBLIC_KEY
```

Platform runners are generated by Flutter, not hand-written. No store signing, store submission or native-device qualification is claimed.

## Actual operating loop

Every minute: inspect active offers; queue fresh checkout/delivery readiness checks; rank eligible offers by contribution and observed demand with a penalty for failed acquisition; queue up to three inbound campaigns per day; answer new enquiries; prioritize open support; request read-only Secure monitoring; request analytics recommendations. Every six hours: inspect configured native Marketing portfolio, website and GitHub sources and discover active Stripe prices explicitly tagged for Manager. Catalog inspection alone never qualifies a product for sale.

Each task has a stable idempotency key, bounded attempts, an exclusive lease and a fencing token. Task completion requires a completed receipt and independent adapter verification. Process crashes recover expired leases. Unknown integrations produce explicit dead-letter blockers. Fix credentials and use owner Retry to resume the same task ID. Positive task spending always needs owner approval. Strategic, legal, enterprise, employment, borrowing, pricing, division and high-risk security tasks require approval regardless of cost and still need an explicitly allowed adapter operation. No arbitrary shell or generated code executes in Manager.

Signed Stripe events are saved before acknowledgement. A separate inbox reconciler continues while autonomous work is paused. Duplicate events, duplicate session IDs and duplicate payment-intent IDs cannot create multiple orders. Payment and refund reconciliation serialize by payment intent. Refunded or sandbox orders cannot be fulfilled. Live one-time payments trigger onboarding, then delivery, then a satisfaction request. Actual satisfaction comes only from separately authenticated feedback ingress, never from a sent message. Test payments never count as a real customer. Owner emails are excluded from the external-customer metric; this does not independently establish buyer identity or rule out collusion/fraud.

## Native sources and offer setup

Configure `SOURCES` for read-only native Marketing `/api/products/portfolio`, GitHub commits and website availability. These calls do not imply those products are ready. Stripe discovery imports only active fixed-price products with trusted administrator metadata `manager_system` and `manager_cost_minor_units`. Alternatively register an immutable offer through owner-authenticated `POST /v1/offers` with `id,name,description,system,stripe_account,price_id,unit_amount,currency,cost_amount`. No `ready` input is accepted. Manager verifies the exact live price/product and requires independently checked delivery/legal/support evidence. Evidence expires after 24 hours and refreshes hourly.

`POST /ingress/leads` receives `{email,need,source,consent,offer_id?}` from a trusted website backend. It records the enquiry; the email adapter may answer the requested enquiry but must not send marketing without consent. `POST /ingress/checkout {lead_id,offer_id}` creates an idempotent Stripe Checkout URL only for an eligible offer. Configure working `/purchase-complete` and `/purchase-cancelled` pages on the first allowed origin. Lead capture UI, bot protection and customer authentication remain website integration work. Existing website payment links may be observed if they use a registered exact Stripe price, but must be tested against Manager's handler.

Separate `STRIPE_ACCOUNTS` keys/webhook secrets keep product accounts isolated. Configure snapshot events at `/webhooks/stripe/<account-id>`: `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `charge.refunded`, and `customer.subscription.created/updated/deleted`. Signing is verified against exact request bytes with a five-minute tolerance at ingress. Internal replay of already-verified, private inbox records rechecks the signature without age rejection. Reconciliation retries eight times; failures appear in `/v1/state` and owner `/v1/webhooks/retry {id}`. No owner console control edits or forges payment data.

**Current billing limits:** fulfillment supports fixed-amount one-time Checkout, one line with quantity one, without discounts/taxes changing the registered total. Subscription events report observed fixed-price MRR/ARR, but subscription Checkout fulfillment intentionally blocks until the invoice/entitlement adapter is qualified. Metered/tiered subscription pricing, disputes, cancellations, partial refund entitlement rules and refund revocation require further implementation. Do not sell unsupported modes through Manager.

## Ecosystem execution contract

`BRIDGES` maps a system to its controlled HTTPS adapter URL, secret token and permitted operations. This repository implements the Manager client; it does not pretend existing apps already expose this contract.

* `GET /manager/v1/capabilities` returns `{version:1,idempotency:true,operations:[...]}`.
* `POST /manager/v1/commands` accepts `{task_id,operation,payload,context,budget_minor_units,policy}` with `Idempotency-Key: task_id`. A retry must return the same remote job. Reserve/enforce the whole cost cap before performing any effect. Reject unsupported operations and untrusted instructions embedded in customer text.
* Return `{id,task_id,status:"accepted"|"completed",evidence:"https://..."}`. `check_offer` also returns `checks:{delivery:true,legal:true,support:true}` backed by actual tests. `GET /manager/v1/receipts/<id>` must independently inspect the real result and return the same completed evidence before Manager marks the task complete.

Operations: `check_offer`, `acquire`, `qualify`, `onboard`, `deliver`, `satisfaction`, `support`, `secure`, `optimize`. Marketing must prove actual publication, not just creation of a draft. Delivery must prove the purchased access/service is available. Email must use verified sender credentials and transactional/consent rules. Secure observation may not perform high-risk remediation. Analytics can recommend but cannot silently change pricing. Missing adapters block work explicitly. No machine credential is extracted from connected ChatGPT apps or copied into Flutter.

## Evidence and limitations

Tests exercise policy, persistence, approval expiry, tamper-resistant application audit, lease fencing, payment/refund idempotency, the customer journey and API authorization. PGlite runs PostgreSQL SQL locally; the separate PostgreSQL concurrency test is skipped without `TEST_DATABASE_URL` and enabled in CI against a disposable `manager_test` database. Flutter analysis, tests, web release build and Docker build passed in CI run 40405101285. See `AUDIT.md` for observed integration evidence and `VERIFICATION.md` for exact check results.

Currency amounts are minor units. Revenue is never summed across currencies. Missing attribution, forecast LTV and gross margin stay `null`. Net contribution uses recorded costs only. Current conversion is lead-to-paying-customer ratio and cancellation ratio is lifetime, not monthly cohort churn. These are operational observations, not complete accounts. A running worker or successful test is not evidence of a real paying customer or a profitable autonomous company.
