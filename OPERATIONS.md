# Operating contract and deployment

This implementation is an initial operational slice, not a production-complete autonomous company. There are no seeded customers, payments, revenue or ready offers. The mission starts paused and persists its state across restarts.

## Run and verify

Node 24.10+ runs TypeScript directly. `cd backend && npm ci --ignore-scripts && npm run check && npm test` runs strict TypeScript, runtime tests and an embedded real PostgreSQL engine schema/RLS test. `npm ci --omit=dev --ignore-scripts` installs the PostgreSQL driver for production. Apply `database/bootstrap.sql` to a dedicated Manager PostgreSQL database, provision a least-privileged runtime role using the commented grants, configure `.env.example` through your host secret manager and run `npm start`. Environment files are not automatically loaded: use host environment variables or `node --env-file=../.env src/server.ts`.

A continuously running container/VM is required; an interactive ChatGPT session does not host this runtime. Configure restart-on-failure, HTTPS termination, request rate limits, monitoring and encrypted backups. Startup fails closed without owner authentication, and production requires PostgreSQL. Local SQLite is strictly a development/testing option.

Flutter source is in `frontend`. Generate platform runners with `flutter create --platforms=web,android,ios .` in that directory, then `flutter pub get`. Supply `MANAGER_API_URL`, `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` with Flutter `--dart-define`. Only the configured Supabase owner ID can access operational data. No service-role keys belong in Flutter. Platform packaging, signing and store submission are not included or verified.

## Register an offer

Owner-authenticated `POST /offers`: immutable `id`, `name`, `system`, positive integer `priceMinor`, integer `marginMinor`, fractional `conversionEstimate` (explicit assumption, not observed conversion), lowercase `currency`, `stripePriceId`, Stripe-hosted `checkoutUrl`, `approvedClaims`, `active:true`, and `evidence:{product:true,delivery:true,checkout:true,legal:true,checkedAt:<epoch milliseconds>,evidenceUrl:<https evidence>}`. Evidence expires after 24 hours. Renewal currently requires a new offer version. The owner must attest real checkout, delivery, legal and product tests; Manager does not fabricate these proofs. Subscription selling is not yet implemented; current checkout is one-time purchase only.

`POST /checkout` with `offerId` and an `Idempotency-Key` creates a real Stripe live Checkout session binding the offer and price. Stripe should send `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `charge.refunded` to `/webhooks/stripe`. Signed events are deduplicated transactionally. Cumulative partial refunds reduce observed revenue; full refunds cancel undispatched delivery tasks. Refunds arriving before checkout are remembered and applied when the purchase arrives. Already-running downstream jobs require adapter cancellation support. Configure this endpoint only on the product-specific Stripe account used for these offers. Do not reuse unrelated app webhook secrets. Owner offer registration derives a public `/buy/<offerId>` URL from `PUBLIC_MANAGER_URL`. Campaign tasks use that URL; it creates a live Checkout session with the binding metadata and redirects the buyer to Stripe. The public route has basic per-process rate limits; configure host-level distributed rate limiting before production. Existing arbitrary payment links do not automatically carry Manager metadata; only correctly bound sessions are recognized.

## Adapter contract

Configured adapters are trusted services with fixed HTTPS origins and separate bearer tokens. They MUST enforce allowed actions, cost ceilings, data ownership, permission scopes, cancellation, no spam, approved claims, and idempotency. Never point the runtime directly at a generic AI prompt endpoint. An adapter must reject unsupported fields/actions rather than infer permission. Inbound-only campaign payloads prohibit paid ads and unapproved claims. Positive or unspecified spending and high-risk/strategic tasks need owner approval. Approval is specific to the immutable task payload; it does not grant general spending authority.

`POST <ADAPTER_URL>/jobs` receives `{taskId,action,payload,approval}` with stable `Idempotency-Key: taskId`. A retry must return the same job, never duplicate a publication, payment or fulfilment. `GET <ADAPTER_URL>/jobs/<taskId>` must independently inspect the real downstream result and return `{taskId,status:"verified",evidenceUrl:"https://..."}` only when completed. Queued or running jobs are retried with the same ID. Calls time out after 30 seconds, retries back off and dead-letter after five attempts. A job needing more time than this window needs adapter-side durable polling/reconciliation before enabling it. Adapter URLs must be controlled operator endpoints; do not accept URLs from customers. Credentials never go in task payloads or audit records.

`POST /ingress/leads` is server-to-server only using `INGRESS_TOKEN`, with `{sourceId,email,need,consent:true}`. The website backend must validate consent, apply bot/rate protection and deduplicate source IDs. It queues qualification/customer-answer work for the support adapter. `POST /ingress/satisfaction` accepts `{paymentId,customerId,response:"satisfied"|"needs_help",evidenceId}` from a trusted customer-feedback service that authenticates the actual customer. Adapter job completion alone never counts as customer satisfaction. No messages are sent by this repository itself.

Owner API: `GET /state`, `POST /mission {running:true|false}`, `POST /approvals {taskId,decision:"approve"|"reject"}`, `POST /tasks {action,payload:{system,maxCostMinor,...}}`. Pause stops new claims; already dispatched work can complete. Read `/state` for failures, evidence, approval queue and unavailable integrations.

## Recovery and limits

Task claims use transactional leases and per-attempt fencing. Network calls occur outside database locks. The stable task ID protects downstream effects across process crashes only if the adapter implements idempotency. Expired claims recover after two minutes. Failures preserve a memory entry and an audit event. Acquisition chooses another ready offer when the current offer exhausts retries. A missing integration is a real blocker, not a simulated success.

Persistence currently uses one locked JSONB aggregate. This is deliberately a first-customer implementation, not a high-volume scalable data model: large audit/payment histories will require normalized tables, indexes, archival and retention. Audit entries are application append-only but not tamper-evident against database administrators. There is no independent backup/restore test yet. Do not claim high-assurance or seL4 security from this code.

Revenue sums are separated by currency. Signed `customer.subscription.created/updated/deleted` events produce observed monthly/annual recurring values for fixed per-unit monthly/yearly plans, with stale-event rejection. The economics section also reports observed churn, realized revenue per customer and measured traffic conversion. Account-wide MRR/ARR, forecast LTV, attribution and marketing ROI remain null until complete reconciliation is connected. `POST /ingress/observations` accepts deduplicated trusted traffic windows, evidence-backed cost receipts and product health samples using the ingress bearer token. These are observations from configured trusted systems, not independently audited financial accounts. Subscription reconciliation, tax/discount accounting, customer-facing checkout/enquiry integration, automatic readiness probes, support SLA, quote negotiation, cancellation workflows, content quality review, a learning optimiser and live product health probes remain to implement. Gross margin currently uses recorded operating costs, not complete accounting cost of goods. This is not a claim that the full requested autonomous commercial system is complete.
